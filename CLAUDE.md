# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a **Serverpod 3.4.3** full-stack Dart/Flutter monorepo with three packages:
- `admin_panel_server` — Dart backend (Serverpod)
- `admin_panel_client` — Auto-generated Dart client library (do not edit manually)
- `admin_panel_flutter` — Flutter frontend (web, iOS, Android, macOS, Windows, Linux)

## Development Commands

### Backend Server
```bash
# Start Postgres + Redis (required before running server or tests)
cd admin_panel_server && docker compose up --build --detach

# Run the server
cd admin_panel_server && dart bin/main.dart

# Apply migrations on boot
cd admin_panel_server && dart bin/main.dart --apply-migrations

# Stop Docker services
cd admin_panel_server && docker compose stop

# Run all integration tests
cd admin_panel_server && dart test

# Run a single test file
cd admin_panel_server && dart test test/integration/test_tools/my_test.dart

# Regenerate client/server code after schema or endpoint changes
serverpod generate
```

```bash
flutter config --enable-macos-desktop --enable-windows-desktop --enable-linux-desktop
```

## Architecture

### Code Generation
`admin_panel_client/lib/src/protocol/` and `admin_panel_server/lib/src/generated/` are **auto-generated** by Serverpod. Never edit these files directly. Edit the source `.spy.yaml` model definitions and run `serverpod generate`.

> **STRICT RULE:** Do NOT modify any files inside `admin_panel_client/` or `admin_panel_server/migrations/`. These are fully auto-generated by `serverpod generate` and any manual edits will be overwritten. This applies even when adding new endpoint parameters or methods — always instruct the user to run `serverpod generate` instead.

### Authentication & Authorization
- Auth is handled by Serverpod's built-in auth module
- Four roles (hierarchy: SuperAdmin > OrganizationAdmin > Manager > User), defined in `role.spy.yaml`
- Four scopes: `AppScopes.admin`, `AppScopes.organizationAdmin`, `AppScopes.manager`, `AppScopes.user` (defined in `admin_panel_server/lib/src/scopes.dart`)
- On server startup (`lib/server.dart`), a default admin is created: `admin@mako.com` / `Mako@123`

### API Endpoints
Endpoints are in `admin_panel_server/lib/src/endpoints/` and grouped by access level:
- `PublicApiEndpoint` — unauthenticated: login, theory retrieval, training/assessment params, module status & certificate submission from external training app (validated by API key), asset/language management. Exposes locale-aware variants (`getTheorySectionLocalized`, `getTrainingParametersLocalized`, …), `getLocales`, and `getRegions`. Every content response is wrapped in a region/locale envelope (`defaultLocaleKey`, `regions`, `supportedLocales`); localized variants additionally embed `requestedLocaleKey`, `resolvedLocaleChain`, and a per-item `resolvedLocaleKey`. `getLanguages` is deprecated but kept for backward compat. **The full Public API request/response reference lives in `PUBLIC_API.md` at the repo root — read it before changing any of these endpoints.**
- `AdminEndpoint` — requires `AppScopes.admin`: org CRUD, user creation, module config, theory/training/assessment content, all-user progress & training history, region/locale CRUD, per-content localization CRUD.
- `OrganizationAdminEndpoint` — requires `AppScopes.organizationAdmin`: scoped to own organization, team CRUD, user creation, content/module config, training history, `My*` localization CRUD.
- `ManagerEndpoint` — requires `AppScopes.manager`: scoped to managed org(s), user creation, content/module config, notifications, training history, `Managed*` localization CRUD.
- `UserEndpoint` — requires login: own permissions, module config, progress updates, training history, password change, `setPreferredLocale`, `getMyLocales`, locale-aware reads (`getLocalizedTheoryChaptersWithProgress`).

### Data Model Relationships
```
UserInfo (Serverpod Auth) ──→ AppUser (custom)
                                ├─ role: Role
                                ├─ preferredLocaleKey: String?
                                └─ organizations: List<OrganizationUserLink>

Organization ──→ managerId (AppUser)
             ├─ users: List<OrganizationUserLink> (junction table)
             └─ contentVersion: int  (bumped on every content mutation)

ModuleConfig ──→ organizationId, defaultLocaleKey
Region        ──→ organizationId (per-org pool: code, displayName, enabled)
LocaleConfig  ──→ organizationId (regionCode, languageCode, localeKey, displayName, isDefault, fallbackLocaleKey?)

TheoryChapter / TrainingParameter / AssessmentParameter / Asset
  └─ *Localization (chapter_id|parameter_id|asset_id, localeKey, content fields)
     with unique (parentId, localeKey) index, cascade-deletes with parent

UserModuleProgress ──→ userId, organizationId (status, deadline, startedAt, completedAt)
TrainingSessionResult ──→ userId, organizationId (criteria scores, timestamp)
ManagerNotification ──→ managerId (auto-created for overdue users)
```

### Frontend State Management (Flutter Riverpod)
- `src/providers.dart` — core: `clientProvider`, `sessionManagerProvider`, `authProvider`
- `core/localization/locale_providers.dart` — `supportedLocalesProvider`, `currentLocaleProvider` (`StateNotifierProvider<CurrentLocaleNotifier, String>`)
- `features/admin/providers/admin_providers.dart` — organizations, all users, module configs, content, regions, locale configs, per-content localization providers
- `features/org_admin/providers/org_admin_providers.dart` — own org, teams, users, content, `My*` localization providers
- `features/manager/providers/manager_providers.dart` — managed orgs, `selectedOrgIdProvider`, `activeOrgIdProvider`, `Managed*` localization providers (keyed by `(orgId, parentId)` records)
- `features/user/providers/user_providers.dart` — own progress, training history, module config (auto-rebuilds on `currentLocaleProvider` change)

`AuthNotifier` listens to `SessionManager`, auto-fetches `AppUser` via `user.getMyPermissions()`, and syncs state app-wide. GoRouter observes `authProvider` via `_AuthRefreshNotifier` and redirects based on role. `CurrentLocaleNotifier` bootstraps from `SharedPreferences` then `AppUser.preferredLocaleKey`, and re-syncs whenever the AppUser arrives post-login.

### Screen Routing (GoRouter)
Role-based redirect in `core/router/app_router.dart`:
- Unauthenticated → `LoginScreen`
- `SuperAdmin` → `AdminShell` (organizations, users, modules, content, locales, training history, settings)
- `OrganizationAdmin` → `OrgAdminShell` (dashboard, teams, users, modules, content)
- `Manager` → `ManagerShell` (overview, team, modules, content, assets, settings)
- `User` → `UserShell` (modules, settings)

### Key Behavioral Patterns
- **Managers can manage multiple orgs**: `getManagedOrganizations()` returns a list; UI uses `activeOrgIdProvider` derived from `selectedOrgIdProvider`
- **Notification auto-creation**: `ManagerEndpoint.getNotifications()` scans progress records and auto-creates `ManagerNotification` rows for overdue users (deadline passed, not completed)
- **Timestamp idempotency**: `startedAt` / `completedAt` are only set once (won't overwrite if already present)
- **External training integration**: `PublicApiEndpoint` accepts training results and certificate submissions from an external training app authenticated via API key (not user session)
- **Authorization by query filtering**: Managers can only access their managed org's data — enforced server-side via `managerId.equals()` and `organizationId.equals()` filters, not just by scope
- **Content versioning**: Every content mutation (module config, theory/training/assessment/assets, regions, locales, localizations) must call `bumpOrgContentVersion(session, organizationId)` from `lib/src/util/version_util.dart`. The `Organization.contentVersion` int is returned in the login response so clients can decide whether to re-fetch cached data.
- **No auto-feed of starter regions/locales**: new orgs are created empty. The admin must visit the Locales screen and add at least one `Region` + one `LocaleConfig` before any localization-write endpoint will accept saves (`ensureLocaleConfigured` is a hard guard).

### Regional Locale Architecture

The project uses a **regional locale system** keyed on `localeKey` of the form `REGION-language` (e.g., `US-en`, `UK-en`, `AE-ar`). Validation regex: `^[A-Z]{2}-[a-z]{2,3}$`.

**Per-org locale catalog:**
- `Region` (per-org pool of `code`, `displayName`, `enabled`).
- `LocaleConfig` (per-org `regionCode`, `languageCode`, `localeKey`, `displayName`, `enabled`, `isDefault`, `fallbackLocaleKey?`).
- `ModuleConfig.defaultLocaleKey` is the org's default (defaults to `'US-en'`).

**Per-content localization tables:**
`TheoryChapterLocalization`, `TrainingParameterLocalization`, `AssessmentParameterLocalization`, `AssetLocalization` — each has a cascade-delete relation to its parent, a unique `(parentId, localeKey)` index, and a `localeKey` lookup index. They hold the actual translated fields (title/description/thumbnail/video for theory; name/description/scoringFeedbacks for params; name/description/url for assets).

**`!persist` content fields on the parent tables:**
`TheoryChapter`, `TrainingParameter`, `AssessmentParameter`, `Asset` keep their content fields (`title`, `name`, `url`, …) as **non-persistent** Dart-only fields with `default=''`. The DB columns are dropped; the Dart classes still expose the fields so the legacy editor code reads and writes them as if nothing changed. On the server:
- **Writes**: `default_locale_writer.dart`'s `write*DefaultContent` mirrors the input's `!persist` fields into the matching `*Localization` row for the org's `defaultLocaleKey`.
- **Reads**: `hydrate*` helpers batch-load default-locale localizations and populate the transient fields in place before returning.

This means legacy editors stay default-locale-only and the localization rows are the source of truth for storage.

**Locale resolution:**
`LocaleResolver.resolveChain(session, orgId, requestedLocaleKey)` returns the ordered fallback chain — requested → `LocaleConfig.fallbackLocaleKey` → org default → system default (`US-en`) — deduplicated and preserving order. `LocaleResolver.firstHit<T>(chain, lookup)` walks it and returns the first non-null match. Use this for both top-level content (per-content `*Localization` tables) and embedded translations (`QuizQuestion.translations`, `LocalizedAiPrompt`).

**AR Expert AI prompt resolution:**
`PublicApiEndpoint._buildModuleConfigPublic` resolves `aiChatPrompt` against the caller `AppUser.preferredLocaleKey` via the locale chain and returns the resolved string in `ModuleConfigPublic.aiChatPrompt`. The full `aiChatPromptTranslations` list is also returned for clients that want to display alternatives.

**Embedded translations still in use:**
- `LocalizedQuizContent` lives inside `TheoryChapter.questions[].translations` (JSON). Resolved client-side via `LocaleResolver.firstMatch` keyed on `t.localeKey ?? t.languageCode`. The `correctAnswer` index is language-independent.
- `LocalizedAiPrompt` lives inside `ModuleConfig.aiChatPromptTranslations`. The `languageCode` field on both is the deprecated legacy key (kept for backward compat); `localeKey` is canonical going forward.

### Flutter UI Localization (`AppLocalizations` / RTL)

UI strings (buttons, labels, validation messages, …) for the **UserShell surface** are localized via Flutter's built-in `gen_l10n`. Content strings (chapter titles, AI prompt, etc.) still come from the regional locale system above.

- ARB sources: `admin_panel_flutter/lib/l10n/app_{en,ar,ta}.arb`. `app_en.arb` is the template (`template-arb-file` in `l10n.yaml`).
- Generated code: `admin_panel_flutter/lib/l10n/generated/app_localizations*.dart`. **Do not hand-edit.** Run `flutter gen-l10n` after touching ARB files (auto-runs on build).
- Usage: `final t = AppLocalizations.of(context); Text(t.modulesPageTitle);`. `nullable-getter: false` in `l10n.yaml` so the getter returns non-nullable.
- `MaterialApp.router` in `main.dart` sets `locale:` from `currentLocaleProvider` via `UiLocaleResolver.fromLocaleKey` (`AE-ar` → `Locale('ar', 'AE')`). Flutter then drives Material's ambient `Directionality` automatically; `ar`/`fa`/`he`/`ur` render RTL.
- **Language & Region card in `AccountSettingsPage` is User-only** — wrapped in `if (appUser?.role == Role.User)`. Other roles author content but don't consume locale-rendered content here.
- The UserShell surface uses **logical** layout APIs (`EdgeInsetsDirectional`, `BorderDirectional`, `PositionedDirectional`, `AlignmentDirectional`, `textDirection: Directionality.of(context)` on directional icons like `chevron_right`/`arrow_back_ios`). Do not introduce raw `EdgeInsets.only(left:/right:)`, `Border(right:)`, etc., in this surface — RTL will break.
- The full localization architecture (two-layer model, contributor workflow, adding a new locale, known limitations) is documented in `LOCALIZATION.md` at the repo root.

### Content Management UX Pattern

For each of the four content types (Theory chapter, Training parameter, Assessment parameter, Asset), Content Management presents **two parallel editor surfaces**:

| Surface | Editing target | Triggered from |
|---|---|---|
| **Main entry editor** (legacy dialog/side-sheet) | Default-locale content (mirrored to the default-locale `*Localization` row server-side) | Row's Edit icon |
| **Localizations dialog** (centered dialog, 640×720) | All non-default locale variants | Row's globe icon |

**Main editors are default-locale only.** They have no language ChoiceChip selector. Quiz/translation sub-editors that used to appear there are gone; the embedded `q.translations` list is preserved on save but only the Localizations dialog writes to it.

**Localizations dialog shell** matches the Add Chapter design:
- `showDialog`-based centered modal, 640×720, `surfaceVariant` background, `radiusXl` corners.
- Sticky header with title + close.
- Sticky `LocaleChipRow` filtered to **exclude the org's default locale** (the default is edited in the main editor; an inline empty-state renders inside the dialog chrome when only the default exists).
- Scrollable form with `SheetSection` headers (`Chapter Details` / `Video` / `Quiz Questions` for Theory; `Parameter Details` / `Scoring Feedback` for params; `Asset Details` for assets).
- Sticky footer: `Delete Locale` (when an existing row is loaded) on the left, `Cancel` + `Save Locale` on the right.

For theory chapters, the Localizations dialog **also edits embedded `LocalizedQuizContent` entries** — saving issues two server calls: `upsert*TheoryChapterLocalization(chapter, loc)` for the chapter-level fields, then `set*TheoryChapterQuizTranslations(chapterId, localeKey, questionTranslations)` (one entry per question, in order). Quiz answer count is derived from the default-locale question's `q.answers.length`; `correctAnswer` index is shared across all locales.

### Critical Constraints & Gotchas

**Serverpod Dart client cannot deserialize `Map<String, dynamic>` returns.**
Any endpoint method returning `Map<String, dynamic>` or `List<Map<String, dynamic>>` is inaccessible from the generated Flutter Dart client — it will throw a silent exception caught by `try/catch`, returning `null`/`false` with no useful error. Only typed model returns work with the Dart client. `PublicApiEndpoint.login` returns `LoginResponse` (typed) for this reason, while the other public endpoints return maps exclusively for the external HTTP training app. After the region/locale envelope change, **every** non-login Public API read returns `Map<String, dynamic>` (including former list endpoints like `getTrainingParameters`, `getAssessmentParameters`, `getAssets`, `getLocales`, and all `*Localized` variants) — confirm any consumer is the external HTTP app, not the Flutter client.

**Every Serverpod model's `toJson()` includes `__className__`.**
This key is baked into code generation and cannot be removed from model definitions. `PublicApiEndpoint` has `_clean()` / `_cleanValue()` recursive helpers that strip it before returning JSON to external HTTP clients. Do not try to remove `__className__` from `.spy.yaml` or generated files.

**`TheoryChapter`, `TrainingParameter`, `AssessmentParameter`, `Asset` have nullable `organizationId`.**
These models use `relation(optional)`, making their `organizationId` field `int?`. Always null-check before calling `bumpOrgContentVersion`:
```dart
if (param.organizationId != null) {
  await bumpOrgContentVersion(session, param.organizationId!);
}
```
Manager endpoint upsert methods receive `organizationId` as an explicit non-nullable parameter, so they can call `bumpOrgContentVersion` directly. Delete methods must fetch the record first, then null-check its `organizationId`.

**`!persist` fields must be nullable OR have a default.**
Serverpod's `!persist` modifier produces a Dart field that's not stored in the DB. The generated `fromJson` reads it as nullable, so the underlying class field must either be `String?` or `String, default='value'`. Using `String, !persist` without a default causes runtime crashes on DB reads (`null as String`). When in doubt, give it `default=''`.

**`.spy.yaml` default value syntax.**
The correct field syntax for database defaults is `default=value, defaultPersist=value`. The property `defaultPersistenceValue` does not exist and causes a generation error.

**`relation(...)` syntax for child tables.**
Cascade-delete relations (`*Localization` children) use `relation(onDelete=Cascade)` **without** a `name=` qualifier — the parent does not need to declare an inverse list. Adding `name=foo` requires the parent to declare a matching `List<Child>?, relation(name=foo)`, and serverpod generate will error if that's missing.

**`AppDataTable` column `alignment` controls both the cell AND the header.**
The `alignment` property on `AppTableColumn` is used to align cell content AND to derive the header label's `mainAxisAlignment`. Use `Alignment.center` for icon-only columns like Actions, `Alignment.centerLeft` for text columns.

**Video playback uses `media_kit`, not `video_player`.**
`main.dart` must call `MediaKit.ensureInitialized()` after `WidgetsFlutterBinding.ensureInitialized()`. The only video screen is `lib/features/user/screens/theory_player_screen.dart`, which uses `Player` + `VideoController` + `Video` widget. Initial-load UI gates on `_isReady` (set when `_player.stream.duration` fires) — the `Video` widget is only mounted once ready, otherwise its built-in spinner stacks on top of any custom loading overlay.

**`NativePlayer.setProperty(...)` does not exist on web.**
The mpv property setters (cache, demuxer-readahead-secs, network-timeout, etc.) used in `_applyNetworkTuning()` only exist on the native `NativePlayer`. The web build resolves `NativePlayer` to a stub class with no such method, so any direct call fails to compile for web. Guard with `if (kIsWeb) return;` and dispatch via `dynamic native = _player.platform;` to bypass the static type check. See `theory_player_screen.dart::_applyNetworkTuning`.

**TabBar default alignment crashes for non-scrollable tabs.**
The app theme sets `TabAlignment.start` globally, which is only valid when `isScrollable: true`. For any new `TabBar`, either set `isScrollable: true` (and `tabAlignment: TabAlignment.start`) or explicitly override `tabAlignment: TabAlignment.fill`.

**Error message hygiene for snackbars.**
Strip the `Exception: ` prefix: `e.toString().replaceFirst('Exception: ', '')`. This is standard across the locale screens; apply it whenever displaying caught exceptions to the user.

### Shared Widget Patterns (Flutter)

**`AppSideSheet.show()`** — used for legacy create/edit forms (asset editor still uses this). `onSave` is an async callback; throw an `Exception` to show an error and keep the sheet open. The Localizations dialog does NOT use AppSideSheet — it uses a centered `Dialog` to match the Add Chapter UX.

**`AppDataTable<T>`** — sortable, searchable, paginated table. Define columns via `AppTableColumn` with `cellBuilder`, `flex`, `sortKey`/`comparator`, `searchValue`, and `alignment`. Rows get hover highlight automatically.

**`AppStatusChip`** — use `AppChipVariant` (`primary`, `info`, `success`, `warning`, `error`, `neutral`) for role/status badges.

**`AppGradientButton`** — primary CTA button; supports `isLoading`, `width`, `icon`.

**`SheetSection`** — section heading with brand-gradient accent bar, used at the top of every editor sub-section. Defined in `shared/widgets/app_side_sheet.dart` so it ships with the side-sheet barrel.

**`LocaleChipRow`** — horizontal chip row for locale selection. Renders filled chips for locales with existing content, outlined `+ ${localeKey}` chips for empty slots, and a star avatar on the default locale (when not filtered out). Used by every Localizations panel.
